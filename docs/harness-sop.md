# Standard Harness Engineering Procedure

## 1. Goals

Organize development through centralized request intake, repository-level execution, cross-repository acceptance, structured releases, and continuous knowledge feedback.

Scope:

- Control repository: `D:\workspace\agent-harness`
- Business repositories: `backend / web-portal / admin-web / mobile-a / mobile-b / mobile-c / miniapp`

## 2. Core principles

- The control repository is the sole development entry point
- Repository artifacts provide long-term memory; conversations are not authoritative system facts
- `brief / impact / execution / design / tasks` form the change contract
- A passing repository check does not mean the request is complete
- Do not issue release conclusions without rollback plans
- Turn incidents and rework into rules, templates, regression cases, or skills

## 3. Role assignments

### 3.1 Business and management roles

- Product/business: propose requests, define success criteria, and confirm acceptance conclusions
- Technical lead: review impact analysis, dependency order, and release risks
- Human reviewer: evaluate correctness, risks, and release readiness

### 3.2 Governance agents

- `change-intake-agent`: Prepare `brief.md`
- `impact-design-agent`: Prepare `impact.yaml`, `design.md`, and `execution.yaml`
- `verification-agent`: Prepare verification results and acceptance records
- `release-agent`: Prepare release records, rollback plans, and monitoring points
- `knowledge-agent`: Prepare `postmortem.md` and knowledge feedback items

### 3.3 Execution agents

- `backend-exec-agent`
- `web-exec-agent`
- `admin-web-exec-agent`
- `mobile-a-exec-agent`
- `mobile-b-exec-agent`

### 3.4 Prototype agents

- `mobile-c-planning-agent`
- `miniapp-planning-agent`

At this stage, `mobile-c` and `miniapp` remain prototype repositories outside the regular execution-agent pool.

## 4. Standard workflow

### Stage 0: local baseline preparation

Goal: confirm repository status, command contracts, and pre-existing failures.

Commands:

```powershell
.\scripts\checks\validate-repos.ps1
.\scripts\bootstrap\verify-workspace.ps1
.\scripts\checks\discover-contracts.ps1
.\scripts\checks\run-local-baseline.ps1
```

Artifacts:

- `reports/local-validation/*`

Gates:

- Do not use repositories without completed local baselines for pre-release decisions

### Stage 1: create a change record

Goal: route requests through the control repository before work begins in business repositories.

Commands:

```powershell
.\scripts\bootstrap\init-change.ps1 -ChangeId CHG-YYYY-NNNN-slug -Title "Request title"
```

Generated by default:

- `brief.md`
- `impact.yaml`
- `execution.yaml`
- `design.md`
- `acceptance.md`
- `tasks/*.md`
- `verification/result.md`
- `postmortem.md`

Gates:

- Do not begin work without a `change-id`

### Stage 2: request intake

Goal: turn unclear requests into structured goals.

Primary files:

- `brief.md`

Specify clearly:

- Business goals
- User roles
- Success criteria
- Non-goals
- Risk notes

Primary owner:

- `change-intake-agent`

### Stage 3: impact analysis and execution orchestration

Goal: identify affected repositories, dependency order, and who may write where.

Primary files:

- `impact.yaml`
- `design.md`
- `execution.yaml`

Specify clearly:

- Affected repositories, modules, interfaces, configurations, and tables
- Dependency order
- Current stage owner
- repo owner
- write scope
- branch / worktree
- runtime_type / registry_ref
- worker_result / review_result
- lock state

Primary owner:

- `impact-design-agent`

Gates:

- Do not split tasks without `impact.yaml`
- Do not develop concurrently without `execution.yaml`

### Stage 4: task breakdown

Goal: create executable task cards by repository.

Primary files:

- `tasks/<repo>.md`

Each task card must include:

- Inputs
- Outputs
- Change boundaries
- Prohibited changes
- Repository verification commands
- Recommended execution agent

Gates:

- Do not begin business-repository development without a task card

### Stage 4.5: worker dispatch

Goal: dispatch the repository-owner roles in `execution.yaml` as actual worker packets.

Commands:

```powershell
.\scripts\orchestrator\dispatch-change.ps1 -ChangeId CHG-YYYY-NNNN-slug
.\scripts\orchestrator\run-role.ps1 -ChangeId CHG-YYYY-NNNN-slug -RepoId backend -PrintPacket
```

Artifacts:

- `runtime/dispatch-state.json`
- `runtime/packets/<repo>-worker.md`
- `verification/workers/<repo>.md`

Gates:

- Do not enter the worker workflow without registry_ref / runtime_type / worker_result / review_result
- Do not begin a repository's no-hand-code execution if its worker packet could not be generated

### Stage 5: repository-level execution

Goal: develop concurrently within repository boundaries without interfering with other writers.

Rules:

- Each agent writes only one business repository
- Only one agent may write a business repository at a time
- Multiple agents must not share a writable worktree
- Record all execution boundaries in `execution.yaml`

Primary owner:

- The execution agent for the corresponding repository

### Stage 6: repository verification

Goal: verify each repository's own changes first.

Typical checks:

- `backend`: `mvn test` / `mvn package`
- `web-portal`, `admin-web`: `npm run build*`
- `mobile-a`, `mobile-b`: `lint / test`

Primary files:

- `verification/result.md`

Gates:

- Do not declare development complete if repository verification fails

### Stage 7: cross-repository acceptance

Goal: verify complete business workflows across repositories.

Primary files:

- `acceptance.md`
- `verification/result.md`

Requirements:

- Record each step of the user workflow
- Record expected and actual results for every step
- Explicitly record remaining risks

Gates:

- A passing repository check does not mean the request is complete

### Stage 8: release governance

Goal: establish safe deployment readiness for working code.

Primary files:

- Release record instance

Must include:

- Affected repositories and branches/commits
- Database/configuration changes
- Release order
- Rollback steps
- Post-release monitoring points

Gates:

- Do not begin deployment preparation without a rollback plan
- Do not issue a release conclusion without acceptance records

### Stage 9: postmortem feedback

Goal: turn problems into system improvements.

Primary files:

- `postmortem.md`

Produce at least one feedback item:

- New rule
- New template
- New regression case
- New skill

Gates:

- Problems must not remain only in conversation history

## 5. Concurrency and conflict resolution

### 5.1 Shareable operations

- Reading the same rule document
- Reading the same skill
- Reading the same read-only MCP service
- Reading the same baseline report

### 5.2 Exclusive operations

- Writing the same primary control-repository artifact concurrently
- Writing the same business repository concurrently
- Multiple agents sharing a writable worktree

### 5.3 Conflict resolution

- Record owners, write scopes, and lock states in `execution.yaml`
- A second agent may only read or append review comments, not write the primary file concurrently
- Record same-level rule conflicts under `Needs confirmation` in `impact.yaml` or `design.md`

## 6. Rule precedence

Fixed precedence order:

1. Safety / environment rules
2. Change contract: `brief / impact / execution / design / tasks`
3. Cross-repository architecture and release gates
4. Business-repository rules
5. Module rules / example implementations
6. Skill procedures
7. Style preferences

Principles:

- Higher-priority rules override lower-priority rules
- Skills cannot override repository rules
- Repository rules cannot override safety or release gates

## 7. Completion criteria

A request is complete only when all of these conditions hold:

- The change record structure is complete
- `brief.md` is complete
- `impact.yaml` is complete
- `execution.yaml` is complete
- `design.md` is complete
- All task cards are present
- Repository verification is recorded
- Cross-repository acceptance is recorded
- Release records and rollback instructions are complete
- The postmortem is archived or explicitly deemed unnecessary

## 8. Operating principle

Define the work in the control repository, execute in business repositories, and return to the control repository for acceptance, release, and postmortem.
